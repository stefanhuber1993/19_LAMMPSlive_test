Chapter 12

Lines, and the depth buffer
that outlives its pass

Bond spokes, the control net and the box outline are drawn as real GL lines, five passes after the geometry — and they are correctly hidden behind the beads without a single line of occlusion code.

Sharing a depth attachment

Here is the trick, and it is one line of Python:

self.shaded_fbo = c.framebuffer(
    color_attachments=[self.shaded_tex], depth_attachment=self.depth_tex
)

self.depth_tex is the same texture object the G-buffer used for depth back in pass 1. It was filled with every bead's hand-written gl_FragDepth, and nothing since has cleared it. So when the line pass binds this framebuffer and enables depth testing, it is testing against the real sphere surfaces — five passes and three intermediate textures later.

c.enable(c.DEPTH_TEST)
c.depth_func = "<="
c.depth_mask = False           # test against beads, don't write
self._line_vao[0].render(mode=c.LINES, vertices=m)

A bond spoke running from one bead to another disappears where it passes behind a third. There is no sorting, no clipping, no per-segment visibility test. Compare what the CPU fallback path in renderer.py has to do (_draw_net_occluded): step along each segment, project each step, compare against a software z-buffer, and draw the visible runs. Reusing the depth attachment replaces all of it.

depth_mask = False

Test against the depth buffer, but do not write to it. Two reasons. First, the lines are drawn with alpha blending, and a blended fragment that writes depth would occlude later blended fragments that should have shown through it — the standard transparency-ordering problem. Second, nothing after this pass reads depth, so writing would be wasted bandwidth. Restore it immediately afterwards (c.depth_mask = True), because GL state is global and the next frame inherits whatever you left behind.

depth_func = "<="

Less-than-or-equal, where the geometry pass used strictly less-than. A line drawn exactly on a bead's surface — a bond spoke starting at a bead centre — would fail a strict test on the pixels where the two coincide. The tolerant comparison lets coincident geometry through.

Two slots, and one that ignores depth entirely

self._line_vbo = [None, None]

The line pass runs twice per frame, from two buffers. The first is depth-tested, as above. The second is not:

// No depth test at all: these are the lines that have to stay
// readable whatever is in front of them -- the cell outline, when
// the cell itself is buried under its own periodic images.

This is a genuine design decision rather than a technical necessity, and _build_gl_lines spells out the reasoning. Once chapter 13's periodic images surround the real cell, the box outline that says this is the real cell is buried inside copies of itself. Depth-correct rendering would hide the one line carrying the most information. So it is promoted to an overlay — and, in the same breath, exempted from the depth cue:

# Un-fogged when it is on top: the depth cue exists to push
# SCENERY into the distance, and once the outline is the only
# thing saying where the real cell is among its images, it is
# annotation rather than scenery.

Scenery obeys the atmosphere; annotation does not. That is a clean way to think about any overlay in a 3D view.

Why lines come after the blur and the tonemap

The pass order puts the lines between depth of field and FXAA, which means they are never defocused and never tonemapped. The comment defends it in one sentence:

"After the blur and the tonemap on purpose: these are drawing, not photography — a defocused box outline reads as a rendering bug, and their colours are already the display-space values theme.py declares."

Both halves are worth having. A blurred annotation looks like something went wrong, even though it is exactly what a camera would do — because the viewer does not model the outline as being in the scene. And the line colours come straight from theme.py as display-space bytes; sending them through the linear-light pipeline and back would require converting them into linear on the way in, which is pointless work to arrive at the same numbers.

They do go through FXAA, though, because a one-pixel GL line is about the most aliased primitive there is.

What the lines encode

_build_gl_lines is CPU-side and per-frame, and it packs a surprising amount of information into line colour and alpha.

Bond spokes: alpha as a strain gauge

offset = abs(norm(pts[a] - pts[b]) - d_opt)
alpha = BOND_PEAK_ALPHA * math.exp(-offset / lam)
if alpha < BOND_MIN_ALPHA: continue

Alpha peaks when a pair sits exactly at the equilibrium spacing and decays exponentially either side, with decay length lam = 0.10 × d_opt. So a bond fades as its pair is stretched or compressed — pull a bead out of the sheet and you watch its spokes dissolve. The minimum-alpha test doubles as the distance cutoff that bounds how many pairs get drawn at all, which is what keeps this O(pairs) Python loop affordable.

Per-vertex colour, and the fog

fog = self._fog(depth[idx], near, far)
r, g, bb = _lerp_color(BOND_3D_COLOR, HAZE_COLOR, fog)

Each endpoint gets its own colour, computed at its own depth, and the GPU interpolates between them along the segment. A single line therefore fogs along its length for free — the far end recedes and the near end does not.

The near/far passed in here are the same cue_range the composite uses on the beads, so a spoke recedes on exactly the ramp the beads do. That is the kind of consistency that is invisible when you get it right and glaring when you get it wrong.

The box outline's dissolving corner

# Per-VERTEX alpha, so the near corner dissolves along the
# edges rather than the whole edge switching off.

A wireframe box always has one corner nearest the camera, and the three edges meeting there sit in front of the whole scene, which reads as clutter. Fading them by depth is the fix — and doing it per vertex rather than per edge is what makes it smooth. Orbit the camera and the fade slides continuously around the box, because it is a function of depth, which changes continuously. Per-edge alpha would make whole edges blink as the nearest corner changed.

The buffer growth pattern

if m > self._line_cap[slot]:
    for obj in (self._line_vbo[slot], self._line_vao[slot]):
        if obj is not None:
            obj.release()
    self._line_vbo[slot] = self.ctx.buffer(reserve=max(1, m) * 7 * 4, dynamic=True)
    self._line_cap[slot] = m
    self._line_vao[slot] = self.ctx.vertex_array(...)
self._line_vbo[slot].write(data.tobytes())

The same grow-only pattern as the instance buffer in chapter 1. The line count genuinely fluctuates frame to frame — bonds appear and vanish as pairs drift through the alpha cutoff — so a naive "allocate exactly what I need" would reallocate constantly. Growing and never shrinking converges to the high-water mark after a few seconds and then costs nothing.

Note that the VAO must be recreated along with the buffer: a VAO stores a reference to the buffer object, and the old one is dangling once you release it. That is the sort of thing that produces a crash somewhere unrelated three frames later.
