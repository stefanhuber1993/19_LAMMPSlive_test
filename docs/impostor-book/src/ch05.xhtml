Chapter 5

The G-buffer: shade it later

Pass 1 does not compute a single pixel of colour. It writes down what is at every pixel and stops. Everything after it is a photograph of a photograph.

Forward versus deferred

The straightforward way to render is forward: as each fragment comes out of the rasteriser, shade it right there — look up the lights, compute diffuse and specular, write the final colour. It is simple, and it has two problems that matter here.

Overdraw. In a dense bead cloud, five or six beads can stack up on the same pixel. Forward shading fully lights all six, then throws five away. You paid six times for one pixel.

Neighbours. Ambient occlusion, outlines, depth of field and antialiasing all need to know about other pixels: what is beside me, what is behind me. A forward fragment shader cannot ask. It sees one fragment and has no access to the rest of the frame.

Deferred shading splits the job in two. Pass 1 rasterises the geometry and writes, for each pixel, the raw material facts — colour, normal, position — into a set of textures. Then, in a completely separate pass, you draw one full-screen triangle and shade every pixel from those textures. By then the depth test has already thrown away the hidden fragments, so lighting runs exactly once per visible pixel, and the shader can sample any neighbour it likes.

That bundle of textures is the geometry buffer, or G-buffer.

Multiple render targets

A fragment shader can write to more than one texture at a time. In GLSL you declare the slots:

layout(location=0) out vec4 o_albedo;
layout(location=1) out vec3 o_normal;
layout(location=2) out vec4 o_viewpos;

and on the Python side you attach three textures to one framebuffer, in that order:

self.gbuffer = c.framebuffer(
    color_attachments=[self.albedo_tex, self.normal_tex, self.pos_tex],
    depth_attachment=self.depth_tex,
)

Position 0 in the list is location=0. One draw call, one fragment shader invocation, three textures written. This is called MRT, and it is what makes deferred rendering practical: the alternative would be rasterising the geometry three separate times.

Why each format is what it is

Texture formats are where deferred renderers are won and lost. Each choice in resize() has a specific reason.

albedo: RGBA16F (4 channels, half float)

# Albedo is f2 (not f1) so a per-bead brightness boost (>1) survives into
# the composite before the final clamp.

An 8-bit texture (f1) stores 0..1 and clamps. But in_bright can exceed 1 — that is the "spotlight" that highlights a tagged cluster — and o_albedo = vec4(albedo * v_bright, v_fade) would silently clip it to white. Half float carries values above 1 through to the tonemap, which is the thing that is supposed to decide how bright is too bright. The fourth channel is the per-bead fade.

normal: RGB16F

A unit vector in −1..+1. Half float gives about three decimal digits, which is plenty — a normal error of 0.001 shifts a highlight by a fraction of a pixel. (Production engines often pack normals into two 8-bit channels using an octahedral mapping and reconstruct the third component; that halves the bandwidth and is not worth the complexity at this scale.)

view position: RGBA32F — full float, and it matters

# Full float for the view position: its z is a world-space distance, and
# the outline pass compares NEIGHBOURING distances against a threshold of
# a couple of thousandths of one -- which is below half-float resolution
# out at the far side of a big box, so f2 here reads as edge noise.

Worth doing the arithmetic on, because it is a lovely example of a format choice with a visible consequence. A half float has 10 bits of mantissa, so near a value of 28 the spacing between representable numbers is about 28 / 2¹⁰ ≈ 0.027. Chapter 9's outline compares neighbouring depths against a threshold of 0.009292 × 28 = 0.26. The quantisation step is a tenth of the threshold — so the depth gradient the outline measures would come out in visible stair-steps, and the outline would sparkle. Full float has 24 bits of mantissa; the step at 28 is 1.7×10⁻⁶. Problem gone.

depth: a depth_texture, with comparison disabled

self.depth_tex = c.depth_texture((width, height))
self.depth_tex.compare_func = ""          # sample raw depth, not a compare

Depth textures default to comparison mode, a shadow-mapping feature where sampling returns "is this nearer than X?" rather than the depth itself. Clearing compare_func makes it an ordinary readable texture.

NEAREST filtering on all three

for t in (self.albedo_tex, self.normal_tex, self.pos_tex):
    t.filter = (c.NEAREST, c.NEAREST)

Linear filtering would blend neighbouring texels. For a colour that is desirable; for a G-buffer it is nonsense — averaging the view positions of a foreground bead and the background behind it gives a point in empty space that belongs to nothing. Every G-buffer read in this renderer wants the value at one specific pixel, so: nearest.

The background test

Every later pass has to distinguish "a bead is here" from "empty sky". The convention this renderer uses costs nothing:

self.gbuffer.clear(0.0, 0.0, 0.0, 0.0, depth=1.0)
...
if (P.z < -1e-4) { /* a bead */ } else { /* sky */ }

The buffer is cleared to zero. Any real bead is in front of the camera, and view space puts "in front" at negative z, so any bead fragment has P.z < 0 strictly. Zero therefore unambiguously means "nothing was written here". You get a free coverage mask out of a channel you needed anyway.

A real bug this convention avoided. The composite pass could in principle test the depth texture instead. It must not, and the comment records why: the depth texture is this framebuffer's own depth attachment. Reading a texture you are simultaneously rendering with is a framebuffer feedback loop, which is undefined in OpenGL. On a tile-based GPU — Apple Silicon — it surfaced as intermittent black tiles. Undefined behaviour rarely announces itself; it shows up as an intermittent artefact on one machine.

What it costs

The sim viewport is 820×900 = 738,000 pixels. Per pixel the G-buffer is 8 bytes of albedo + 6 of normal + 16 of position + 4 of depth = 34 bytes. Add the downstream buffers and the whole pipeline holds:

bufferformatsize
albedoRGBA16F5.9 MB
normalRGB16F4.4 MB
view positionRGBA32F11.8 MB
depthDEPTH243.0 MB
occlusion × 2 (half res)RG16F1.5 MB
lit (composite output)RGBA16F5.9 MB
shaded, finalRGBA8 × 25.9 MB
total38 MB

That is the deferred bargain stated in bytes: you trade about 38 MB of video memory and 25 MB per frame of write bandwidth for the ability to shade each visible pixel once and to let every effect see its neighbours. On any GPU made this decade it is an obviously good trade. On a mobile chip with 8 MB of tile memory it would not be, which is why mobile renderers still favour forward.

The resize dance

Every one of these textures is sized to the viewport, so all of them are torn down and rebuilt when the window changes:

def resize(self, width, height):
    if width == self.width and height == self.height:
        return
    ...
    self._release_fbos()

The early return matters: resize() is called every frame from the renderer, and rebuilding ten textures per frame would be a disaster. The release() matters too — Python's garbage collector does not know about GPU memory, and a dropped reference to a moderngl texture does not free the VRAM until the object is finalised, which may be much later or never. Explicit release is the rule for every GL resource in the file.
