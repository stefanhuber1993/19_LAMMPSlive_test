Chapter 6

The screen-space trick

Once the G-buffer exists, the screen is a database of the scene: 738,000 rows, four columns, indexed by pixel. Every effect in the rest of the book is a query against it.

The full-screen triangle

Every pass from here on draws exactly one triangle covering the whole screen, so that the fragment shader runs once per pixel. The vertex shader is a small piece of showing off:

void main() {
    vec2 p = vec2((gl_VertexID << 1) & 2, gl_VertexID & 2);
    uv = p;
    gl_Position = vec4(p * 2.0 - 1.0, 0.0, 1.0);
}

There is no vertex buffer at all. gl_VertexID is a built-in counter — 0, 1, 2 — and the bit arithmetic turns it into corners:

gl_VertexID(id<<1)&2id&2uvgl_Position.xy
000(0, 0)(−1, −1)
120(2, 0)( 3, −1)
202(0, 2)(−1,  3)

A giant right triangle with corners at (−1,−1), (3,−1) and (−1,3). Only the lower-left quarter is on screen, and that quarter is exactly the whole viewport. The uv varying runs 0..1 across the visible part for free, because the corners were chosen so that uv and clip position stay in lockstep.

Why a triangle rather than two triangles forming a quad? GPUs shade in 2×2 pixel blocks, and along a shared diagonal the blocks straddling it get shaded twice — once for each triangle. That is a few percent of wasted work on every full-screen pass, and there are six of them here. A single triangle has no interior seam. It also needs no vertex buffer, which is why _build_static_buffers can create the VAOs with an empty attribute list:

self._fs_vaos = {p: c.vertex_array(p, []) for p in (...)}

The one function everything is built on

The G-buffer is indexed by screen position. But the questions the effects want to ask are about 3D space: "is there anything at this point half a bead-radius above the surface?" So you constantly need to go from a view-space point to the texture coordinate where the G-buffer stores what is there. That is view_to_uv:

uniform vec2 projScale;

vec2 view_to_uv(vec3 p) {
    vec2 ndc = projScale * p.xy / max(-p.z, 1e-6);
    return ndc * 0.5 + 0.5;
}

It is chapter 2's projection with everything unnecessary removed. projScale is (P[0][0], P[1][1]) — the fx and fy from the projection matrix, uploaded per frame:

proj_scale = (float(proj[0, 0]), float(proj[1, 1]))
self.ssao_prog["projScale"].value = proj_scale

No matrix multiply, no w: two multiplies, one divide, one multiply-add. Worked example, the bead from chapter 2 at view (2, 0, −12):

ndc = (1.0839 × 2 / 12, 0.9876 × 0 / 12) = (0.18065, 0)
uv  = (0.5903, 0.5)
     → pixel (484.1, 450.0), which is where chapter 2 said it lands.

The max(-p.z, 1e-6) is not paranoia: sample points can land behind the eye, and the division would blow up or flip sign. Clamping puts them harmlessly far off-screen, where the bounds check that always follows a view_to_uv call rejects them.

The assumption baked in. The comment says it: "Assumes a SYMMETRIC frustum, which proj_matrix above always builds." A symmetric frustum has zeros in P[0][2] and P[1][2], so those terms can be dropped. If you ever add a lens shift or an off-centre frustum — VR does, tiled rendering does — this two-line function silently gives wrong answers everywhere, and the symptom would be occlusion sliding sideways as you look around.

What screen space can and cannot know

This is the honest limitation, and it is worth stating plainly because it governs everything in chapters 7–11.

The G-buffer holds the nearest surface at each pixel. Everything behind that surface is gone. So a screen-space effect can answer "what is the nearest thing along this pixel's line of sight?" and nothing else. In particular:

  • An occluder hidden behind another object cannot cast a shadow or occlude anything — the buffer has no record of it.
  • An occluder off the edge of the frame cannot either. Pan the camera and shadows near the border change.
  • How thick an occluder is has to be guessed, since only its front surface is stored. Chapter 7's shadowThick is exactly that guess.

The code comment gets the trade-off exactly right: "That costs missing shadows, not ugly ones, which is the right way round." A screen-space effect fails by omission — something that should have been dark is merely lit — and an omission reads as a slightly flatter picture, not as a bug. Compare the failure mode of shadow maps, which is a hard black band across a wall.

What you buy for that is enormous: cost proportional to pixels, not to scene complexity. Seven beads or fifteen hundred, the occlusion pass does the same 184,500 pixels of work.

Noise instead of pattern

Screen-space effects are all approximations built from a handful of samples, and a handful of samples means error. The trick that makes that error acceptable appears twice in this file:

float hash12(vec2 p) {
    vec3 p3 = fract(vec3(p.xyx) * 0.1031);
    p3 += dot(p3, p3.yzx + 33.33);
    return fract((p3.x + p3.y) * p3.z);
}

A hash: take the pixel coordinate, multiply by irrational-looking constants, throw away the integer parts, mix the components together, throw away the integer part again. The specific constants have no meaning — they are chosen so nearby inputs land far apart in the output. Given a pixel it returns a repeatable pseudo-random number in 0..1.

Both the occlusion and the shadow march use it to rotate or offset their sampling pattern per pixel. The comment states the principle better than I can:

"it trades structured error (banding, terracing) for unstructured error of the same size, which reads as texture instead."

This is genuinely worth internalising, because it is not obvious. The amount of error is unchanged. But the eye is superb at seeing structure and poor at seeing noise: sixteen shadow-march steps at the same spacing on every pixel produce sixteen visible terraces marching across the image, and the same sixteen steps offset randomly per pixel produce a fine dither that the blur in chapter 8 turns into a smooth gradient. Same error, entirely different picture.

The R2 sequence

The ambient-occlusion loop wants points spread evenly over a disc. White noise clumps — random points leave gaps and clusters, and with only eight samples the clumping is the dominant error. So it uses a low-discrepancy sequence instead:

vec2 xi = fract(vec2(float(i) * 0.7548776662,
                     float(i) * 0.5698402909) + rot);

Those two constants are the R2 sequence: the fractional parts of 1/φ and 1/φ² where φ is the plastic number (the real root of x³ = x + 1), the two-dimensional analogue of using the golden ratio in 1D. Successive points fill the unit square with far more even coverage than random ones, so eight samples behave like considerably more. The + rot is the per-pixel hash from above, sliding the whole sequence so neighbouring pixels use different points.

Note the comment: "no bit operations, so it works in GLSL 330". The more common low-discrepancy choice, the Hammersley sequence, needs a bit-reversal, and the integer intrinsics for that arrived in GLSL 400. The renderer targets 330 because macOS caps out at OpenGL 4.1. That is a real constraint shaping a real code choice, and it will shape yours too.
